# Formic 任务设计与提示词

Formic 最擅长把同一项语义工作稳定地执行很多次：每个 worker 取得一份分片，按共同规则
独立使用 LLM 和只读工具，最后发布一条可以单独验收的记录。它不是负责拆解目标的项目
经理，也不是让多个 worker 互相讨论后维护一份全局结论的协作系统。

调用方负责两件事：先把数据划成语义独立的单元，再在需要时统一处理全部单元结果。
Formic 负责中间的大规模独立执行阶段。

## 1. 最佳调用前提

开始作业前，应当能够对下列问题全部回答“是”：

| 问题 | 成立时的含义 |
| --- | --- |
| 同一份规则能否用于所有单元？ | worker 共享一份 `task.md`，只替换末尾分片 |
| 每个单元是否有明确且有限的主范围？ | worker 知道主动处理什么，也知道何时停止 |
| 单元能否在看不到其他单元结果时完成？ | 正确性不依赖其他 worker 的输出或完成顺序 |
| 单独重试一个单元是否安全？ | 重试不会修改共享业务事实，也不会使其他结果失效 |
| 并发变化是否只影响耗时？ | 先完成谁不应改变结果含义 |
| 单元结果能否独立验收和保存？ | 部分成功有价值，失败单元可以单独补做 |

任一项不成立时，不应靠提示词假装它成立。应当改变分片方式，把依赖步骤移到作业前后，
或改用一个拥有全局视图的处理者。

如果工作只是确定性的解析、精确计算或固定格式改写，并不需要模型判断或工具查证，普通
程序通常更便宜、更稳定。如果整个目标只有一项全局决策，也没有自然的独立单元，直接交给
一个全局处理者通常更合适。

## 2. 适合与不适合的工作

| 适合 Formic | 不适合作为同一批独立单元 |
| --- | --- |
| 按共同准则抽取每个文件、记录或行区间中的事实 | 读取所有单元后才能做出的最终结论 |
| 对大量独立对象进行分类、审阅或合规核验 | 全局去重、统一命名、总排名或唯一编号分配 |
| 从当前分片发现候选，再到只读输入或远端来源核实 | 让 worker 根据其他 worker 的新结果继续派生工作 |
| 把每个单元转换成同一结构化数据契约 | 需要共享可变状态、事务或严格执行顺序的流程 |
| 对独立证据集进行分析，允许个别单元失败后重试 | 没有停止条件、会不断扩大候选范围的开放式探索 |

“全局处理”并不是整个工作中不能出现。正确做法是先让 Formic 产出独立记录，再由一个
明确的统一汇总者读取全部记录并作出决定。若后续阶段还能重新划分成互不重叠、互不依赖的
单元，可以由调用方启动另一个 Formic 作业；否则它就应保持为单一汇总步骤。

## 3. 怎样选择分片大小

分片应以最小的完整语义范围为边界，不能只按文件字节数平均切割。一个单元必须同时满足：

- 分片中包含作出单元判断所需的主要上下文；
- 任务说明、当前单元文件或行区间、工具 schema、输出预算和安全余量能够进入模型上下文；
- 单元失败后可以只重试这一小块，而不重做大量已经确认的工作；
- 单元数量不会小到让固定的模型请求和档案开销压过实际工作。

初始任务、当前分片和冻结工具目录不能靠历史压缩变小。若它们本身超过安全预算，
worker 会直接失败。因此，大文件应按能够独立理解的记录边界或行区间切分；只有相邻对象
必须共享上下文时才把它们放进同一单元。不要为了减少单元数而制造超大分片，也不要为了追求
高并发把一个完整语义对象切碎。

## 4. Worker 实际知道什么

Formic 自动向每个 worker 提供：

- 作业内字节一致的系统 instructions；
- `task.md` 原文；
- 当前单元的文件内容或行区间，以及对应相对路径；
- 完整 `input` 根可按需通过 `search`/`read` 检索的说明，但不重复列出全量文件；
- 作业启动时冻结并稳定排序的工具名称和参数 schema；
- 结构化模式下的结果 schema 和内部提交工具。

`task.md` 不必重复这些事实。尤其不要把 unit 编号、总单元数、分片路径、并发数、缓存、
重试、模型名或 MCP 连接信息再次写进任务说明。重复的动态内容会浪费上下文，还会破坏不同
worker 共享的 prompt cache 前缀。

worker 可以通过内置工具读取整个 `input`，也可以看到当时已经发布到 `output` 的数字编号
记录。这两者含义不同：

- `input` 是当前单元可用的只读证据库；
- `output` 是随完成顺序变化的观察窗口，不是完整快照，也不是协调机制。

因此，单元可以跨分片核实自己的候选事实，但不能依赖 `output` 判断“其他 worker 已经处理
到哪里”、决定全局唯一性或等待另一项结果。否则并发数一变，语义也会改变。

## 5. 提示词必须交代什么

一份可执行的 `task.md` 应当明确以下七项内容。

### 5.1 单元目标

用一句话说明当前 worker 要交付什么，以及这条记录供谁或哪个后续步骤使用。目标必须是
单元级结果，不能写成只有汇总全部输出后才可能完成的总目标。

### 5.2 主处理范围

明确“主动发现只发生在当前分片”。如果允许跨分片或联网查证，说明查证必须由当前分片内
哪个对象或疑点触发，不能把查证过程中遇到的新对象无限扩张成新的工作清单。

### 5.3 纳入与排除规则

写出能够按字面执行的判断条件，包括边界情况。避免“尽可能全面”“深入分析”“酌情处理”
这类无法验收的要求。若两个规则冲突，应明确优先级。

### 5.4 证据要求

说明什么来源可以作为事实、每个结论需要多少证据、如何记录位置，以及证据冲突时如何
处理。证据位置应使用输入相对路径和行号、远端来源地址或工具能够稳定返回的定位信息，
不要只写无法复查的概括。

### 5.5 工具使用条件

模型已经收到工具 schema，不必在提示词中抄写参数。提示词应说明使用工具的目的、触发
条件和停止条件，例如“仅在当前证据不足时查找反证，取得一项直接支持和一项冲突检查后
停止”。不要要求为了显得认真而遍历所有工具。

配置决定模型看得见哪些工具，自然语言不能代替能力边界。操作者可以完整开放已配置的
MCP，也可以按当前作业筛选；Formic 不替用户作决定。无论选择哪种方式，需要的能力都应在
作业开始前完成发现和校验，提示词只说明使用条件。

Formic 只知道 MCP 公布的名称、schema 和返回值，不能自行判断一个远端工具是否会修改
外部状态。带副作用的工具只有在每个单元操作互不冲突、调用可安全重试或服务端提供必要
保护时才适合并发使用；实际并发和风险由操作者决定。

### 5.6 不确定与失败

规定证据不足、内容冲突、工具失败、结果截断或对象不适用时的表示方法。允许明确的
`unknown`、`conflicting` 或空结果，比要求模型猜出一个肯定答案更可查。

### 5.7 输出含义与完成条件

文本模式说明最终文档必须包含哪些部分。结构化模式由 JSON Schema 约束形状，`task.md`
仍需解释每个字段表达什么、依据是什么、什么时候允许空值。不要机械抄写 schema，也不必
再次要求调用内部提交工具；系统 instructions 已经负责提交协议。

最后写出可判断的停止条件：当前分片的所有主对象都已处理，每项结论都满足证据或不确定性
规则，且结果符合输出契约。不要把“继续搜索直到没有任何可能遗漏”当作停止条件。

## 6. 通用提示词模板

下面的模板只表达职责，不绑定具体领域。删除不适用的段落，并把尖括号内容替换为当前
任务的可验收规则。

```markdown
# 单元目标

只处理“你的分片”中的 <主对象>，为每个对象产出 <单元级结果>。这些记录将由
<后续使用者或步骤> 统一消费。

# 范围

- 当前分片是唯一的主动发现范围。
- 可以在完整 input 或指定外部来源中查找与当前对象直接相关的支持或反证。
- 查证命中不得自动成为新的主对象；不要处理其他单元，也不要推断全局完成状态。

# 判定规则

1. 当 <可观察条件> 成立时，记录 <结论>。
2. 当 <排除条件> 成立时，不纳入结果。
3. 规则冲突时，按 <明确优先级> 处理。

# 证据

- 每项结论至少需要 <证据要求>。
- 记录 <相对路径与行号、来源地址或其他可复查位置>。
- 证据冲突时标记 <冲突状态>，保留双方依据，不自行消除冲突。

# 工具

- 只有在 <触发条件> 时才使用 <能力类别>。
- 取得 <足够证据> 或达到 <明确停止条件> 后停止查证。
- 工具错误或结果截断时，按不确定性规则记录，不重复无进展调用。

# 不确定性

证据不足时输出 <规定表示>；不要根据常识补全输入中没有且工具未证实的事实。

# 输出

每条记录表达 <字段或段落的语义>。只提交当前单元能够负责的事实；不要生成全局唯一名称、
全局排名、跨单元去重结果或任务运行信息。

# 完成条件

当前分片中的主对象均已按上述规则处理，所有结论都有证据或明确的不确定状态，且输出符合
当前契约后立即提交。
```

## 7. 结构化输出的职责分配

字段应由真正掌握该事实的一方填写：

| 事实类型 | 责任方 | 处理方式 |
| --- | --- | --- |
| 当前分片内的观察、分类、证据和不确定性 | worker | 放入单元 schema，由模型提交并本地校验 |
| unit、分片位置、任务时间、重试和工具耗时 | Formic 运行时 | 由文件名、worker 档案和 stats 记录，不要求模型重复 |
| 全局标准名称、合并组、总顺序和最终统计 | 调用方的汇总步骤 | 读取全部单元记录后统一决定 |

把全局字段提前交给独立 worker，会产生互相冲突的“最终事实”；把运行时字段交给模型，
则会浪费 token 并引入本来不存在的出错机会。schema 应只保存当前单元真正能够判断的内容。

## 8. 跨分片查证的正确边界

跨分片查证仍然可以保持单元独立，前提是查证对象来自当前分片，目的只是验证当前单元的
结论。可以按下面三条判断：

1. 如果删掉其他 worker 的全部输出，本单元仍能完成；
2. 如果工具在别处找到新对象，本单元不会因此改变自己的主动处理清单；
3. 如果所有单元同时查到同一份证据，它们只记录各自结论，不争夺全局所有权。

只要其中一条不成立，任务已经从证据检索变成跨单元协调，应当修改计划或增加作业后的
统一处理步骤。

## 9. 常见错误

- **让每个 worker 建立完整全局目录**：每个单元看到的起点和完成时刻不同，无法产生同一
  权威结果。改为输出当前分片的候选与证据，之后统一归并。
- **让 worker 读取 `output` 去重或认领对象**：结果取决于并发完成顺序。改为允许重复的
  单元事实，并由统一汇总者处理。
- **把远端搜索当成无限发现入口**：工具调用会不断扩张任务，无法定义完成。改为先固定
  单元对象，再只查与它直接相关的证据。
- **把所有总体要求塞进每个单元**：模型会尝试完成自己没有全局视图的工作。只保留会改变
  当前单元判断或输出的要求。
- **只写“输出 JSON”而不解释语义**：形状正确不代表内容可用。使用 schema 约束形状，
  用任务说明定义字段含义和证据标准。
- **要求输出详细思维过程**：这既不是可靠证据，也不是 Formic 的可观测性来源。运行档案
  已记录实际请求、响应、工具调用和状态变化；提示词只要求结论与可复查依据。

## 10. 启动前检查清单

- [ ] 每个单元有唯一、有限的主动处理范围。
- [ ] 初始分片和冻结工具目录能够进入安全上下文预算。
- [ ] 单元不依赖其他 worker 的结果或完成顺序。
- [ ] 跨分片和远端检索都有触发条件与停止条件。
- [ ] 纳入、排除、冲突和证据不足都有明确规则。
- [ ] `task.md` 没有重复运行时已经提供的分片、并发或工具参数。
- [ ] 单元输出没有混入全局去重、命名、排名或最终汇总字段。
- [ ] 结构化 schema 只包含 worker 能够负责的事实，并解释了字段语义。
- [ ] 已由操作者决定完整开放或主动筛选 MCP，提示词没有把自然语言当成权限控制。
- [ ] 调用方已经确定如何消费、校验和必要时汇总单元记录。

满足这些条件后，扩大单元数量或调整并发只会改变吞吐和完成时间，不会改变任务本身的
责任边界。
