# Formic 任务设计

Formic 最适合把同一种语义工作稳定地执行很多次：每个 worker 获得一份明确分片，独立读取证据、调用工具并发布一条可单独验收的结果。它不是让多个 worker 互相讨论后维护一份全局结论的协作系统。

调用方负责拆分和最终归并，Formic 负责中间的大规模独立执行。

## 1. 判断任务是否适合

开始前检查：

| 问题 | 必须成立的原因 |
| --- | --- |
| 同一份规则能否用于全部单元？ | 所有 worker 共用一份 `task.md` |
| 每个单元是否有明确且有限的主范围？ | worker 才知道主动处理什么、何时停止 |
| 看不到其他 worker 结果时能否完成？ | 并发顺序不能改变正确性 |
| 单独重试一个单元是否安全？ | 失败不应使其他结果失效 |
| 单元结果能否独立保存和验收？ | 部分成功才有价值 |
| 调整并发是否只改变耗时？ | 否则任务依赖共享状态或顺序 |

任一项不成立时，应改变分片方式，把依赖步骤移到作业前后，或交给一个拥有全局视图的处理者。不要靠提示词假装单元独立。

确定性解析、精确计算和固定格式改写通常直接写程序更便宜、更稳定。Formic 的价值在于需要模型判断、证据核实或多轮工具调用的独立任务。

## 2. 适合与不适合

| 适合 | 不适合作为同一批 worker |
| --- | --- |
| 逐文件、逐记录抽取事实 | 全局去重、统一命名和总排名 |
| 对大量对象分类、审阅、核验 | 等待其他单元完成后才能判断 |
| 从当前对象出发查找支持或反证 | 让工具命中无限扩张为新任务 |
| 逐对象补齐结构化元数据 | 分配全局唯一编号或共享所有权 |
| 独立证据集分析，允许个别失败重试 | 需要共享事务或严格执行顺序 |

需要全局处理时，先让 Formic 产出独立记录，再由一个明确的汇总步骤读取全部结果。若第二阶段还能重新划成独立单元，可以启动新的 Formic 作业。

## 3. 怎样选择分片

分片应以最小完整语义对象为边界，而不是简单平均文件字节数。

一个单元应同时满足：

- 分片包含作出判断所需的主要上下文；
- 当前对象可以与其他单元独立处理；
- 失败后只需重试这一小块；
- 任务、分片、工具 schema 和输出契约能进入模型安全上下文；
- 固定请求与档案开销不会明显大于实际工作。

初始任务、分片和工具目录不能靠历史压缩变小。大文件应按记录、章节或其他完整语义边界切分。只有相邻对象必须共同判断时才放入同一单元。

## 4. Worker 能看到什么

Formic 自动提供：

- 作业内一致的系统说明；
- `task.md` 原文；
- 当前单元的文件、图片或行区间；
- 完整 input 可按需通过只读工具检索的说明；
- 冻结并排序后的工具名称和参数 schema；
- 结构化模式下的结果 schema 与内部提交工具。

`task.md` 不要重复 unit、总单元数、分片路径、并发、缓存、重试、模型名或 MCP 连接信息。

`input` 是稳定的只读证据根。`published` 模式下可见的 output 只是随完成顺序变化的观察窗口，不是完整快照或协调机制。

## 5. 任务说明必须包含什么

### 5.1 单元目标

一句话说明当前 worker 要交付什么，以及结果由谁或哪个后续步骤使用。目标必须是单元级结果。

### 5.2 主处理范围

明确主动发现只发生在当前分片。允许跨分片或联网查证时，写明由当前分片中的哪个对象或疑点触发。

工具找到的新对象不能自动变成新的主任务，否则工作会无限扩张。

### 5.3 判断规则

写出可以按字面执行的纳入、排除和优先级规则。避免只有“尽可能全面”“深入分析”“酌情处理”等无法验收的要求。

### 5.4 证据规则

说明允许的来源、每项结论需要什么证据、怎样记录位置，以及证据冲突时如何表示。输入证据使用相对路径和行号，远端证据保留可复查地址或工具定位。

### 5.5 工具条件

模型已经收到工具 schema，任务说明只需写使用目的、触发条件和停止条件。例如：“当前字段缺少直接证据时才搜索；取得一项直接来源并完成一次冲突检查后停止。”

不要要求为了显得认真而遍历全部工具。自然语言也不能代替配置和权限边界。

Formic 只知道 MCP 公布的名称、schema 和结果，不能判断远端工具是否会修改外部状态。带副作用的工具只有在各单元互不冲突，并且调用可安全重试或服务端提供必要保护时才适合并发开放。

### 5.6 未知与失败

规定证据不足、内容冲突、工具失败、结果截断和对象不适用时的表示方法。明确的 `unknown`、`conflicting` 或空值通常比猜测更可靠。

### 5.7 输出和完成条件

文本模式说明最终文档需要哪些部分。结构化模式由 schema 约束形状和可机械判断的范围，任务说明仍要解释字段含义和何时使用空值。需要显式区分“字段已处理但没有值”时，把字段列入 `required`，并使用 `["string", "null"]` 这类 nullable 类型表达结果。

完成条件应能判断，例如：“当前分片所有主对象都已处理，每个字段有证据或明确未知状态，结果符合 schema 后立即提交。”

## 6. 独立元数据补全示例

这类工作可以直接使用 Formic，但要让每个 worker 只负责一个独立对象或一组不会互相影响的对象。

### 6.1 输入

```text
data/
├─ item-001/
│  ├─ source.txt
│  ├─ cover.png
│  └─ metadata-template.txt
└─ item-002/
   ├─ source.txt
   └─ metadata-template.txt
```

计划：

```jsonl
{"unit":1,"files":["item-001/source.txt","item-001/cover.png","item-001/metadata-template.txt"]}
{"unit":2,"files":["item-002/source.txt","item-002/metadata-template.txt"]}
```

每个单元的任务材料包括初始数据和一份等待补齐的元数据表。worker 可以从当前对象出发读取完整 input，或调用允许的联网 MCP 查证，但不能把搜索中新发现的其他对象加入自己的处理清单。

### 6.2 推荐输出状态

每个字段至少区分：

| 状态 | 含义 |
| --- | --- |
| `confirmed` | 有满足要求的直接证据 |
| `conflicting` | 来源互相矛盾，保留双方依据 |
| `unknown` | 已按停止条件查证，仍无可靠答案 |
| `not_applicable` | 字段对当前对象不适用 |

使用独立的 `status` 表达以上四种情况，并把字段值、状态和证据作为不同事实写入 schema。允许字段没有值时，用 nullable 类型保存 `null`，为空字符串保留其真实业务含义。

### 6.3 任务说明示例

```markdown
# 目标

只补齐“你的分片”中元数据模板已有的字段。最终记录将由后续汇总程序直接消费。

# 范围

- 当前分片中的对象是唯一主动处理对象。
- 可以读取完整 input，或联网核实与该对象直接相关的字段。
- 搜索中出现的其他对象只可作为证据，不得成为新的处理对象。

# 证据

- 优先使用当前对象的原始材料和权威来源。
- 每个 confirmed 字段记录至少一项可复查位置。
- 来源冲突时标记 conflicting，保留双方值和来源，不自行选择一个无依据答案。

# 未知

完成当前材料检查和一次针对性外部查证后仍无可靠答案，标记 unknown；不要根据常识猜测。

# 输出

保持模板字段含义，只填写当前对象能够负责的值、状态和证据。不要生成跨对象排名、全局唯一名称或运行信息。

# 完成条件

模板中的每个字段都有 confirmed、conflicting、unknown 或 not_applicable 状态，且所有非未知结论都有可复查依据后立即提交。
```

若使用结构化输出，schema 可以把每个字段建模为包含 `value`、`status` 和 `evidence` 的 object，并用 `enum`、`const`、长度或数值范围表达可机械判断的约束。unit、重试次数和工具耗时由运行时记录，模型 schema 只保留结果消费者需要的事实。

## 7. 通用任务模板

```markdown
# 单元目标

只处理“你的分片”中的 <主对象>，为每个对象产出 <单元级结果>。结果将由 <消费者> 使用。

# 范围

- 当前分片是唯一主动发现范围。
- 可以在完整 input 或指定外部来源中查找与当前对象直接相关的支持或反证。
- 查证命中不得自动成为新主对象，也不要推断全局完成状态。

# 判断规则

1. 当 <条件> 成立时，记录 <结论>。
2. 当 <排除条件> 成立时，不纳入结果。
3. 规则冲突时，按 <优先级> 处理。

# 证据

- 每项结论需要 <证据要求>。
- 记录 <相对路径和行号、来源地址或其他位置>。
- 证据冲突时使用 <冲突状态>，保留双方依据。

# 工具

- 只有在 <触发条件> 时才使用 <能力>。
- 取得 <足够证据> 或达到 <停止条件> 后停止。
- 工具错误或结果截断时按未知规则记录，不重复无进展调用。

# 未知

证据不足时输出 <规定表示>；不要补全未被输入或工具证实的事实。

# 输出

每条记录表达 <字段或段落语义>。只提交当前单元能够负责的事实。

# 完成条件

当前分片主对象均已处理，所有结论有证据或明确未知状态，且输出符合当前契约后立即提交。
```

## 8. 跨分片查证边界

跨分片查证仍可保持独立，但必须同时满足：

1. 查证对象来自当前分片；
2. 删除其他 worker 的全部输出后，本单元仍能完成；
3. 工具发现的新对象不会扩大主动处理清单；
4. 多个 worker 查到同一证据时，只记录各自结论，不争夺所有权。

任一条件不成立时，任务已经变成跨单元协调。

## 9. 常见错误

- **让每个 worker 建完整全局目录**：改为只输出当前分片候选与证据，之后统一归并。
- **读取 output 去重或认领对象**：结果会依赖并发顺序；允许单元事实重复，由汇总步骤处理。
- **把远端搜索当无限发现入口**：先固定主对象，只查与它直接相关的证据。
- **把总体要求塞进每个单元**：删除当前 worker 无法负责的全局目标。
- **只写“输出 JSON”**：schema 约束形状，任务说明仍要解释字段语义和证据。
- **要求详细思维过程**：运行档案记录可观察事实，任务只要求结论和可复查依据。

## 10. 启动前清单

- [ ] 每个单元有唯一、有限的主动处理范围。
- [ ] 单元不依赖其他 worker 的结果或完成顺序。
- [ ] 初始分片和工具目录能进入模型安全上下文。
- [ ] 跨分片与远端查证有触发条件和停止条件。
- [ ] 纳入、排除、冲突和证据不足有明确规则。
- [ ] 任务说明没有重复运行时自动提供的信息。
- [ ] 输出不包含全局去重、命名、排名或最终汇总字段。
- [ ] schema 只包含当前 worker 能够判断的事实。
- [ ] 操作者已经决定 worker 输出权限和 MCP 暴露范围。
- [ ] 调用方知道怎样消费、校验和必要时归并结果。
