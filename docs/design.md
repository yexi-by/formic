# Formic 设计文档

> 状态：**候选设计**。本文件描述尚未实现的架构决策，依据是需求推演与参考实现
> （`reference/codex`、`reference/grok-build`）的结构分析。决策在实现并验证后以代码
> 为准，届时本文件同步修订为事实描述；与代码冲突的一方按现行契约修正。
>
> 范围：本文件当前覆盖外部调用方式、语义边界、执行单元形态、工具治理、数据可见性
> 与原型内置工具、输入构造、失败/重试与断点续跑权责、规模验证。分片规划（数据切分）
> 与结果汇总均为调用方权责，不在运行时设计范围内。

## 1. 参考结论

**主参考：codex**（`reference/codex/codex-rs`）。形态同构：headless、单次会话、
CLI 进出、产出即毁。

- `core/src/session/turn.rs`：单文件 turn 循环（LLM ↔ 工具调用），无交互概念夹带。
- `exec/src/lib.rs`：headless CLI 驱动会话、消费事件、输出结果的形状。
- rollout crate：响应项增量 JSONL 持久化 —— 运行记录与审计的参照（跨运行续跑权责
  在调用方，见第 8 节，rollout 的会话恢复机制不采用）。
- `core/src/tools/orchestrator.rs`：「选沙箱 → 执行 → 重试」工具流水线；摘除审批环
  即为 worker 的权限模型。
- 提示词分层：`client_common.rs` 的 `Prompt`（instructions 顶层字段 + tools schema
  + input items），见第 7 节。

**局部参考：grok-build**（`reference/grok-build`）。

- `crates/codegen/xai-grok-sampler/src/stream/`：多套模型 API 各写一个 stream
  transform，统一输出内部事件枚举 —— 模型无关分层，主循环不感知后端差异。
- `crates/common/xai-tool-runtime/src/tool.rs`：Tool trait 形状；ToolStream 不变量
  「若干 Progress + 恰好一个 Terminal」。
- 停滞检测与重试预算：批处理场景防止单 worker 死循环烧 token 的防线。
- `xai-grok-agent/templates/prompt.md` 与 `synthetic_reason` 注入标记：提示词静态/
  动态切分与注入消息来源标记的参照。

**不参考**：两者的 TUI 与交互协议（ACP）、插话与审批等交互概念；grok 的
session-per-thread 线程模型；codex 的大配置面与大体量系统提示词（那是通用交互
agent 的行为伤疤，批处理 worker 的世界不存在这些约束）。Formic 的 worker 无人
插话、无人审批、无 UI 渲染，交互概念不引入。

## 2. 外部调用方式：一次调用 = 一个批处理作业

调用方（人或上游 Agent）是规划者，Formic 是执行者。**文件系统是唯一的接口面**：
不要 daemon、不要会话协议——调用方给文件、等结果、看目录。

这一形态同时是**嵌入式理念**的落点：Formic 是被嵌入其他流程的组件，不是自成一体
的应用。不开端口、不发明协议、不需要 SDK，文件与目录就是全部接口——人、Agent、
CI 或另一个程序，都能零成本地把它嵌进自己的流程。

**输入**：一次命令，形如
`formic run --data <dir> --plan <plan.jsonl> --task <task.md> --concurrency <N> --out <dir>`。

- 数据根：整个输入数据集目录（可见性边界见第 6 节）。
- 分片计划：JSONL 文件，一行一个单元——自然编号 + 分片范围（文件清单或行区间）。
  几千条分片放不进 argv，必须是文件；人和上游 Agent 都能稳定生成。启动时校验：
  每个分片落在数据根内、不为空；错误报文件名与单元号。
- 并发数：槽位窗口大小，调用方唯一的策略选择。
- 任务说明：自然语言文本文件，运行时原样搬运（语义边界见第 3 节）。

**输出**：输出区目录本身就是仪表盘。每个单元的产出是一条独立记录，**以计划中的
单元编号为键**，原子发布（先写临时、提交后一次性可见）。调用方任何时刻读到的都是
完整记录的集合，永远读不到半截。等待模式结束时 stdout 给简短汇总：完成数、失败数、
失败单元号。

**控制**：进程生命周期 = 作业生命周期。等待 = 等进程退出，退出码区分全部成功 /
部分完成 / 被终止；停止 = 终止进程（上游 Agent 作为父进程天然持有句柄）。没有
控制 API。

调用方的交互只有三种：**等待**（阻塞到最后一个单元完成）、**观察**（中途读输出区，
监督整体是否符合预期）、**决定**（继续或终止）。「中途观察再决定」之所以安全，
由第 8 节的调用方续跑规则保证：终止不是破坏，重跑零成本。

**权责边界**：数据切分（分片规划）与结果汇总均为调用方职责。运行时保持极简——
不生成计划、不合并产出；输出区即交付物。

## 3. 语义边界：Formic 不理解自然语言

Formic 对自然语言只做「搬运」，不做「理解」。理解语义的只有两处：worker 背后的
LLM，以及调用方（含中途监督时的上游 Agent）。

- Formic 对任务说明的全部操作是机械的：读文件、校验结构（存在、大小有界、编码
  合法）、原样装配进 prompt（见第 7 节）、记入审计。装配 ≠ 理解。
- Formic 严格理解的是**结构**：tool call 的 JSON schema、消息格式、计划文件格式。
  语义在黑箱（LLM）内，结构在黑箱外，Formic 拥有黑箱外的全部——输入如何构造、
  输出如何解析，完全可控、可查、可复现。
- 三个推论：
  - **模型无关免费成立**：Formic 不依赖任何语义判断，换模型不动运行时。
  - **质量责任各归各位**：输出「结构不对」是 Formic 的失败（重试、诊断）；「结构对
    但内容不好」不是——归任务说明、模型能力或分片规划，由中途监督闭环发现处置。
  - **可完整压测**：Formic 对 LLM 的要求只有「遵守协议形状」，不要求「聪明」，因此
    mock LLM server 能驱动全链路（见第 9 节）。

## 4. 执行单元（worker）= 单协程

每个 worker 是一个 tokio task。

**理由**：worker 不执行任意代码。其全部代码路径由运行时自身构成——构造 prompt、
调用 LLM、向调度器请求工具——不持有任何未治理资源的句柄。因此用**能力隔离**
（无句柄即无能力）替代 codex 式 OS 沙箱：沙箱存在是因为 codex 的 agent 带用户凭证
执行任意 shell 命令，Formic 的 worker 没有这条路径。tokio task 为几 KB 状态机，
panic 由 JoinHandle 捕获、不波及其他 worker；几万并发在 task 层面无压力。

**任务拓扑**：每 worker 恰好一个 task。SSE 流解析放在 worker 循环内，用 `select!`
与取消令牌竞争；不引入 codex 的 mapper task 层（其作用是为交互场景解耦背压，批
处理无此需求）。取消用 CancellationToken 树：运行时级 token → 每 worker child
token → 模型流与工具调用再向下派生，一处取消全树收敛。

**规模模型**：

- **任务总量无界，活动槽位有界**。窗口大小的唯一依据是外部硬限制（LLM API 配额），
  不由实现猜值。「几万 worker」的含义是排队总量无界、窗口内活跃有界，窗口满时
  排队等待，不转化为容量错误。
- 真实成本是**每 worker 的对话历史内存**（1 万 × 1MB = 10GB 量级）。历史预算与
  压缩阈值是规模化的前置条件，取值须有实测依据（见第 9 节），不作为拍脑袋配置项。

## 5. 统一调度器：工具调用的唯一入口

worker 不直接调用工具，一切工具调用经调度器转发。调度器不是转发层，它拥有以下
不变量：

- **限流与窗口准入**：LLM 与 web fetch 分别记账，互不挤占。
- **结果大小硬边界与超时**：工具结果将注入模型上下文，必须有界。
- **去重与缓存**：多 worker 请求同一外部资源只发一次（批处理中必然发生）。
- **审计**：每次调用的输入与输出完整可追踪、可复现。
- **只读 enforcement**：worker 可见的调用命名空间中没有写动词。

**形状：治理集中、执行并发**。调度器串行完成 O(1) 的准入、查重、记账，执行本身
spawn 到并发任务（有界），结果经 oneshot 返回请求方。串行保证不变量，并发保证
吞吐，避免调度器在万级 worker 下成为热点。

## 6. 工具集与数据可见性

### 6.1 数据可见性边界

单个 worker 的读边界不是自己的分片，而是两棵根，此外的文件系统一律不可见：

- **输入根**：整个输入数据集，对全部 worker 只读共享。分片只是任务分配单位，
  不是可见性单位——检索分片之外的上下文是正当需求（如查术语在全书的出现）。
- **输出根**：其他 worker **已完成**的任务输出，只读。只暴露已提交并记入权威
  状态的记录（写入方提交后原子可见），在途的部分输出不可见，读取方不会读到
  半截结果。这条不变量同时服务中途监督与调用方续跑（见第 2、8 节）。

工具不向模型暴露原始文件系统路径：调用的范围参数是枚举（`input` / `output`）
加根内相对路径或 glob，绝对路径一律拒绝，遍历不跟随逃逸根目录的符号链接。
边界由构造保证，而非事后校验。

### 6.2 原型内置工具：search（唯一一个）

原型只实现一个工具，模型侧按意图命名 `search`（rg 是实现，不是契约）。引擎用
ripgrep 的库 crate（`grep-regex` / `grep-searcher` / `ignore`）进程内嵌，不 spawn
rg 子进程——协程模型下不为单次调用付进程成本，调度器才能直接治理。

- 入参：模式（regex 或字面量）、范围（`input` / `output` + 可选根内 glob）、
  上下文行数。Rust `regex` crate 保证线性时间，向模型开放 regex 无 ReDoS 风险。
- 出参硬边界：匹配数上限 + 总字节上限 + 单条上下文上限；截断必须在结果中显式
  标记，不得静默丢弃。
- 执行：搜索是 CPU 密集操作，放入有界 blocking 池（按 CPU 核数），不占运行时
  线程——与「治理集中、执行并发」一致。
- 不需要 read_file / list_dir：worker 的分片内容随任务下发，数据集文件清单随
  任务说明给出。原型期 search 覆盖唯一真实缺口「越过自己分片找上下文」。

### 6.3 只读分级原则

- **本地只读**：无副作用，从宽治理。
- **外部读取**（web fetch）：语义为读，但每次都是出站副作用，消耗外部配额、可被
  对方限速封禁。必须经调度器限流与缓存，不得当作免费读操作。原型不实现；将来
  需要时经同一治理路径进入。
- **结构化输出不是工具**：worker 没有任何写动词，结果只能经运行时统一输出通道，
  在产出即毁时持久化到磁盘（通道约定见第 7 节）。
- 任何引入代码执行能力的工具（如 shell）不属于内核；若将来出现，必须由调度器
  以独立隔离方式执行——协程共享地址空间，能力隔离对任意代码无效。

**可拓展性保障**：Formic 能向任何方向轻松发展，依赖的不是内核预留的扩展点，而是
内核概念最少、每项规则有唯一语义所有者、对外契约（计划文件、任务说明、工具接口、
输出通道）稳定。新能力在内核之外生长，不改内核。这与 AGENTS.md 总纲一致：可拓展性
通过删减获得，不通过预留获得。

## 7. 输入构造（worker prompt）

参照 codex 与 grok-build 的共同分层（顶层 instructions + tools schema + input
items），按批处理原型裁剪为三块：

**系统提示词（instructions）**：Formic 代码拥有的静态文本，全 worker 字节一致、
会话内不改。原型只含三小段：

1. **角色与自主性条款**：你是一次性自主执行单元；没有人在场回答你的问题——不要
   提问、不要请示，根据任务说明自行判断，完成后交付并停止。（聊天模型遇不确定
   默认提问，批处理里提问 = 卡死占槽，这是批处理特有、可预知的第一条行为约束。）
2. **search 工具使用规则**：两棵只读根（input / output）、结果截断标记的含义。
3. **通道约定**：你的最后一条消息就是你的产出，运行时原样持久化；无法取得进展
   时说明原因并停止，不要重复相同操作。

不写 personality、formatting、输出 schema——那些是通用交互 agent 的行为伤疤，
批处理不存在；**输出格式的语义要求由调用方写进任务说明**，不进内核提示词
（语义边界见第 3 节：Formic 管通道的机械性，调用方管内容的语义）。

**工具信息**：走请求的 tools 字段（JSON schema：name / description / parameters），
不放提示词文字。原型只有 search 一个。

**用户消息**：首条 = 任务说明原文 + 分片内容与定位 + 数据集文件清单。**任务说明
在前、分片在后**——同一作业内全部 worker 的「instructions + 任务说明」前缀字节
一致，prompt cache 跨 worker 命中；分片内容各不相同，置末尾。单会话 agent 只需
考虑会话内缓存，Formic 在万级 worker 规模下吃跨 worker 缓存，这是成本大头。

**运行时注入**（重试说明、停滞警告等）：用枚举标记消息来源（参照 grok 的
`synthetic_reason`），与任务说明文本严格区分，不靠文本猜测「谁在说话」。

## 8. 失败、重试与断点续跑

**运行内（Formic 权责）**：

- 单 worker 失败不波及其他 worker：task panic 由 JoinError 捕获。调度器是单点，
  其代码路径须保持无 panic 纪律。
- 每项任务成败独立：已确认且一致的进展及时落盘，不做整体成败。
- **停滞检测**：worker 重复相同 tool call 达到阈值即终止该 worker 并记录结构化
  诊断（参考 grok-build）。
- **重试预算**：单 worker 重试次数有界（瞬时故障：限流、超时、协议错误），耗尽
  即判失败，诊断随结果记录。

**跨运行（调用方权责）**：

- **断点续跑不由 Formic 负责**。Formic 跨运行无状态，每次调用是独立作业——这消除
  了跨运行状态一致性这一整类 bug，运行时零新增概念。
- 续跑 = 调用方读输出区、生成**剔除已完成单元**的新计划、再次调用。输出区里的
  已完成记录就是完成事实的权威表示；监督与续跑共用同一机制（读输出区）。
- 对 Formic 的硬要求只有两条，且均是已有设计的自然延伸：输出记录**以计划单元
  编号为键**（调用方据此算差集）、**原子可见**（见 6.1，中途读到的永远是完整
  记录）。
- 进度粒度 = 单元。进程被终止时在途 worker 的进度自然丢弃：没产出记录的就是没
  完成，续跑计划自然包含，不需要任何中途 checkpoint。
- 计划是权威输入：调用方若重复分配已完成单元，Formic 照常执行并以新记录替换，
  不做特殊处理——重复分配是调用方自己的成本。

## 9. 规模验证（先于大规模实现）

以 mock LLM server（可控延迟、返回固定 tool call 序列）驱动 5000 个 worker 全链路：

- 观测内存曲线，验证历史体积是主导内存项；
- 观测调度器记账路径耗时与邮箱深度，验证治理集中未形成热点；
- 为槽位窗口、历史预算、压缩阈值提供实测值。

该实验验证的不是「能否开 5000 个 task」（答案已知），而是上述真实风险点。
暴露的问题转化为测试用例与校验规则。
