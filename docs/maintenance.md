# Formic 维护指南

本文承接具体工程维护方法。项目根目录的 `AGENTS.md` 只保存宏观方向；模块、命令、字段、检查矩阵和发布步骤以本文及当前代码为准。

## 1. 开始改动前

先完成四件事：

1. 从用户可见结果说明目标、成功、失败和必须保持的行为；
2. 沿[项目地图](project-map.md)找到拥有该规则或状态的模块；
3. 搜索全部当前调用方、同语义实现、测试、配置和文档；
4. 选择能够证明真实入口结果的最小验证范围。

不要从用户最先提到的函数或报错位置直接决定改动范围。调用方只做转发时，应在真正拥有语义的位置修正。

代码、测试和旧文档都只是证据。事实冲突时，先检查生产调用链和当前外部契约，再决定修正哪一方。

## 2. 当前工程契约

### 2.1 单一当前版本

Formic 的 CLI、配置、作业清单、结果格式和内部协议只实现当前契约。确认变更后，在同一次改动中替换生产代码、测试、配置示例和文档，并删除旧字段别名、格式探测、双读双写和兼容分支。

旧输入只按当前规则报告无效，不需要识别它来自哪个历史版本。确需迁移既有业务数据时，应由明确的独立任务授权，不在生产解析器里长期保留迁移逻辑。

### 2.2 独立单元

并发和完成顺序只能改变耗时，不能改变单元结果含义。新增能力若要求 worker 等待其他结果、争夺全局所有权或修改共享业务状态，应重新划分作业边界，而不是在 worker 循环中增加协调协议。

`published` 是显式辅助读取能力，不改变上述原则。测试隔离语义时应改变并发完成顺序，确认 `none` 下结果不受其他单元影响。

### 2.3 资源窗口不是任务总量

`max_concurrent_units`、工具并发、请求频率和缓存容量限制活动资源。窗口满时后续工作等待，不能把合法单元总量、工具调用总量或对话回合数转成容量错误。

固定上限必须由外部硬限制、可复现故障或测量证据支持。仓库正式默认值面向大规模作业；降低默认值时同步更新代码、配置示例、文档和规模证据。

## 3. 代码和依赖边界

模块职责见[项目地图](project-map.md)。维护时遵循以下直接依赖规则：

- `main.rs` 负责组合和生命周期，不复制配置、计划、工具或输出规则；
- worker 只消费协议无关 LLM 事件和 Scheduler 响应；
- 普通工具不能绕过 Scheduler；
- 协议模块不决定业务完成、重试预算或发布；
- 输出格式与审计校验只由 `output.rs` 拥有；
- 计划、配置和外部工具参数分别只在各自边界解析一次；
- 内部提交工具不进入普通工具注册表。

只有当前存在替换、独立测试、多实现或隔离需要时才引入 trait 或新抽象。代码形状相似但规则、错误或生命周期不同的实现应保持独立。

新增字段、类型或持久状态前，明确写入方、读取方、权威位置、创建时机和失效条件。没有当前消费者的内容不加入生产接口。

## 4. 配置维护

配置只表达部署环境、外部服务和操作者可长期选择的策略。固定产品语义留在代码中。

新增配置字段必须同时完成：

1. `FileConfig` 定义；
2. 环境覆盖规则（若确有需要）；
3. 边界解析和类型化校验；
4. 生产调用方消费；
5. 缺失、非法、冲突和覆盖测试；
6. `config.example.toml` 与 `docs/usage.md` 更新；
7. 若影响续跑语义，加入作业清单身份并验证变化在远端请求前失败；
8. 若存在本机 `dist/config.toml`，按用户授权同步，但不得把其中密钥加入 Git、日志或回复。

配置采用严格未知字段拒绝。不要为尚未实现的能力预留开关，也不要用默认值掩盖必填的外部选择。

配置示例使用“一段短注释对应一段配置”。注释说明操作者要做的选择和直接后果，不逐行复述字段名。

`extra_body_json` 是明确的原样透传边界：只接受 object，保留 JSON 类型，不能覆盖协议管理字段。增加协议管理字段时同步更新冲突集合和三协议测试。

## 5. CLI、计划和任务输入

### 5.1 CLI

CLI 参数在 `main.rs` 定义。新增或改变参数时核对：

- 首次运行与 `--resume` 是否都需要；
- 缺失值在哪个阶段失败；
- 退出码是否保持 0/1/2/3 的现行含义；
- README、详细使用说明和真实 `formic run --help` 是否一致；
- 变化是否属于作业不可变身份。

面向人的输入输出只使用自然 unit、文件名、字段名和简短业务名称，不暴露 hash、UUID 或内部请求 ID。

### 5.2 计划

`plan.rs` 是两种分片形状和路径合法性的唯一所有者。增加分片能力时，从计划解析一直验证到首条模型消息，不在 worker 中猜测新的 JSON 形状。

文件分片可承载文字和支持图片；行区间只承载 UTF-8 文本。路径检查、目录 capability 和冻结 input 共同构成边界，任何一层都不能改成 ambient 路径重新打开。

### 5.3 Prompt

同一作业的 instructions、任务说明和工具目录应尽量保持字节稳定，当前分片追加在用户消息末尾。不要把可从 unit 顺序、计划或已验证状态稳定推导的事实重复发给模型。

新增模型输入必须说明模型如何消费它，以及缺少它为何会导致当前输出错误。任务设计规则属于 `docs/task-design.md`，不要硬编码领域提示词。

## 6. LLM 与多模态维护

### 6.1 协议无关内核

共同历史、工具请求、完成类别、usage 和错误分类先在 `llm/mod.rs` 建模。供应商模块只翻译协议形状。若一项能力不能在三个协议中保持同一业务含义，应先明确边界，不能在 worker 中按协议堆分支。

新增消息内容或工具结果类型时，检查：

- 三种请求映射；
- 三种流式响应与终态；
- 历史重放；
- token 预算；
- 上下文压缩；
- 审计表示；
- 错误和取消；
- 端到端请求体。

### 6.2 可审计边界

worker 档案必须能够检查协议无关输入如何构造、模型通过验收后返回了什么、工具调用如何配对，以及在哪一步失败。

以下内容不得进入终端、stats 或 worker 档案：

- API key、Authorization 和秘密 header；
- 实际请求 URL；
- HTTP 错误正文；
- SSE envelope、残帧和无效协议 payload；
- reqwest 或传输库原始错误文字；
- 图片 data URL 或 base64；
- Responses opaque/encrypted replay payload。

允许公开的供应商错误事实限于 HTTP 状态、公开服务类别、allowlist 中的 code 和已解析 `Retry-After`。

### 6.3 请求预算

文字估算必须覆盖当前协议的实际请求结构、工具 schema、扩展 JSON和需要重放的供应商项，同时排除图片 base64。视觉 token 按已解码尺寸和协议规则单独加入，所有求和使用 checked arithmetic；失败时宁可拒绝请求，也不能低估为可发送。

首条分片装配可以流式做保守预算，但完成后仍用真实内部历史重新估算一次。压缩候选只能切完整工具往返，初始用户消息不可压缩。

### 6.4 图片

图片格式、签名、尺寸、原始字节与来源事实统一经过 `image_input.rs`。本地分片、`read_image` 和 MCP 图片不能各自建立不同校验。

新增格式时同时检查：

- 最小依赖 feature；
- 扩展名、MIME、签名和尺寸读取；
- 三协议编码；
- 留档扩展名；
- 损坏、MIME 不符和分配失败；
- 公开产物无 base64；
- 上下文压缩和活动历史释放。

不要自动下载 URL、转码、缩放或设置没有证据的图片常量上限。

## 7. 工具、缓存与 MCP

### 7.1 内置工具

`tools.rs` 同时拥有 schema、参数默认、路径权限、结果截断和缓存键规范化。若 schema 允许某参数，运行时必须解析并消费；运行时拒绝的权限不能只依赖模型遵守 schema。

阻塞文件系统和图片读取应在 blocking task 中执行。取消在队列、文件块、行、匹配和长循环边界传播。错误结果不可缓存；截断结果只有在当前契约明确允许时才缓存。

### 7.2 Scheduler

所有普通工具统一经过 Scheduler。修改调度时验证：

- 收件箱满时等待而非报总量超限；
- 不同 server 的许可互不占用；
- 取消在准入前不会启动工作；
- 排队和执行时间含义不混淆；
- cache hit、joined、miss 和 bypass 保持可区分；
- 同一模型回合的普通工具调用同时进入调度器，并按模型原始调用顺序回注结果；
- 单 worker 的并发调用仍服从全局、server 和单工具资源窗口。

### 7.3 MCP

MCP 目录在 worker 启动前发现并冻结。stdio 与 Streamable HTTP 的消息大小、会话、超时和取消在传输边界处理；模型名称和别名在目录冻结时一次校验。

已发送但结局未知的远端调用绝不自动重放。`reconnect=true` 只允许下一次新调用建立新会话。收到明确结果后的本地转换或媒体留档失败，也不能重新发送远端调用。

新增 MCP ContentBlock 类型时，必须确定当前模型消费者、公开表示、结果容量、存档、安全边界和三协议传递方式。没有消费者的资源类型保持明确不支持。

## 8. 状态、输出与续跑

### 8.1 作业身份

只有会改变同一输出目录结果解释的事实才进入作业清单。新增不可变事实时必须说明首次写入方、续跑读取方和变化后为什么不能安全复用旧结果。

续跑校验必须发生在 MCP 初始化和 LLM 请求之前。旧清单不迁移；结果文件、状态和 schema 任一不一致时保持现场并明确失败。

### 8.2 原子发布

结果、schema、状态和档案始终相对启动时绑定的输出目录 capability 操作。不要在运行中重新按环境路径打开 output。

结果先写同目录临时文件，再通过 rename 公开；已存在结果不可覆盖。发布门把取消和结果提交线性化。失败 worker 不留下完成记录，已经发布的其他单元不回滚。

### 8.3 审计与统计

状态事件只能描述已经发生的事实。完成事件必须在对应阶段结束后写入，普通统计不能提前使用“已发布”或“成功”语义。

worker 审计完整性是发布条件；stats 和进程 metrics 是派生证据，写入失败不应改写已经确定的业务结局。修改审计字段时同步更新序列化、逐行校验、Markdown 渲染和失败测试。

## 9. 错误和失败语义

边界错误、环境失败、远端服务失败和内部不变量破坏保持不同类型。控制流依赖类型化事实，不解析 Display 文本。

面向用户的错误只说明对象、直接原因和修改方法。不得倾倒内部状态、数据库式标识、供应商请求 ID 或敏感正文。

允许的未产出、部分可用和不可用状态应保留结构化原因；只有当前模块无法继续履行契约时返回错误。不要吞掉异常或伪造成功，也不要用无依据默认值继续运行。

## 10. 测试策略

测试保护当前可观察行为、外部契约和必要不变量，不保护实现细节或文档措辞。生产代码和测试不得读取 Markdown 文档来决定或断言业务行为。

修改前分别说明：

- 前提是什么；
- 执行哪个真实入口或模块契约；
- 预期观察到什么结果、状态和副作用；
- 哪种反例能够推翻当前方案。

常用验证：

```bash
cargo fmt --check
cargo test
cargo clippy --all-targets -- -D warnings
cargo +1.88.0 check --all-targets
```

按改动范围增加：

| 改动 | 额外验证 |
| --- | --- |
| CLI、配置、作业身份 | 启动失败必须在 MCP/LLM 请求前；检查首次运行和续跑 |
| LLM 协议 | 三协议请求体、SSE 事件、工具回合、usage 与失败终态 |
| 图片 | 四格式、混合分片、MCP、公开产物、压缩与失败分配 |
| 工具权限 | schema 与伪造参数都验证；改变并发完成顺序 |
| MCP | 真实 fake stdio/HTTP、分页发现、超时、取消、重连不重放 |
| 输出与续跑 | 真实二进制入口、原子发布、损坏现场和取消竞态 |
| 并发、内存、缓存、状态规模 | release 规模实验与资源曲线 |

规模实验命令：

```bash
cargo run --release --example scale_run -- 5000 1000 8 20
```

四个参数依次是单元数、worker 并发、每单元工具回合数和 mock 延迟毫秒。它会生成被 Git 忽略的 `scale-metrics.csv`；该文件只用于性能分析。

warning 也是验证结果。当前改动引入的 warning、失败或未分类诊断必须处理；与本次范围无关的既有问题应在交付时说明。

## 11. 文档维护

文档按下列责任更新：

| 变化 | 应更新的位置 |
| --- | --- |
| 项目定位、最短用法、关键能力 | `README.md` |
| CLI、配置、计划、工具、输出、续跑 | `docs/usage.md` |
| 模块、依赖、状态或数据流 | `docs/project-map.md` |
| 维护方法、检查矩阵、发布流程 | `docs/maintenance.md` |
| 单元边界和提示词写法 | `docs/task-design.md` |
| 档案、统计、状态和排错 | `docs/observability.md` |
| 长期宏观项目原则 | `AGENTS.md` |

文档只描述已实现且有证据的当前行为。候选方案明确标为候选，不创建“暂时兼容”说明。删除或重命名文档时，搜索并修正仓库内全部链接。

修改 `AGENTS.md` 时，读取全局和项目规则，确认完整指令链不超过当前 `project_doc_max_bytes`，并在新会话验证关键规则确实加载。具体模块和命令不应重新搬回 `AGENTS.md`。

## 12. 发布与本机 dist

源码的 release 构建：

```bash
cargo build --release
```

在 Windows 上，真实产物是 `target/release/formic.exe`。更新本机 `dist/formic.exe` 前：

1. 完成与改动风险相称的测试、Clippy 和 MSRV 检查；
2. 运行 release 产物的 `run --help` 或最小真实入口；
3. 明确获得覆盖旧发布程序的授权；
4. 用精确绝对路径复制，不递归操作目录；
5. 比较源与目标 SHA-256；
6. 使用 `dist/config.toml` 做不触发远端请求的解析 smoke test。

`dist/` 和本机 `config.toml` 被 Git 忽略。不要把真实 API key、MCP bearer、私有路径或发布二进制加入提交。仓库中的 `config.example.toml` 只能保存无密钥示例。

## 13. 提交前交付检查

完成改动后：

1. 检查 `git status`，区分用户已有改动和本任务差异；
2. 查看实际 diff，确认没有旧实现、旧链接、密钥和无关文件；
3. 运行相称验证并保存退出结果；
4. 按全局要求执行 pre-commit review；
5. 只暂存本任务文件，检查暂存差异；
6. 提交边界清楚的中文提交；
7. 再次确认工作区状态，并只声明已经验证的结果。

若用户已有改动与本任务无法安全分离，不提交并明确说明；不要为了提交而覆盖、回滚或夹带用户内容。
